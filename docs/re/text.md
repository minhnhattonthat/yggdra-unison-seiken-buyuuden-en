# Text engine

## Encoding (verified: decoded MESSAGE001/MESSAGE085/SPMES002003 lines read as natural Japanese)
- Shift-JIS appears only in debug labels (`ST%02d.BIN` stage names `ＳＴＡＧＥ００` at 0x16, never drawn as far as seen) and font kanji lists; all game text is glyph-index encoded.
- **Code = glyph index in the font the screen uses.** Every font is an NTFT file: 16x16 px, linear 4bpp rows of 8 bytes, 128 bytes/glyph (same layout as a 3D 16-colour texture), palette in the matching NTFP. Ink is the low palette indices (1-3 core, up to ~8 anti-alias), 0xF border = outline.
  - byte `00..EF` = glyph `b`;
  - `F1+n, xx` (n = 0..4) = glyph `0xF0 + n*0x100 + xx` (system text uses F1-F3 only);
  - `FD` = new line, `FF` = end of string. **No other control codes exist** in any dialogue/system string (inventory below). Names are spelled out, never inserted by a code.
- **Control-code inventory (verified, `tools/msgscan.py`):** over all 11,482 MESSAGE/SPMES/TUTO strings the only non-glyph bytes are FD (4,556) and FF; system strings (`tools/systext.py`) likewise.

## Bytecode script files (MESSAGE/SPMES/TUTO) - verified by coverage
- Header: `u32 ?` (0/1/file id), `u32 n`, `u32 table_off` (0xC), then n x u32 entry offsets into the bytecode (event entry points; each entry ends with opcode `01`). Bytecode follows; strings follow the bytecode, FF-terminated, to EOF (zero padding allowed).
- Strings are referenced only by absolute file offsets in two opcodes:
  - `30 xx <u32 off>` (xx = 00/01): show message.
  - `51 <u32 off>`: string argument (SPMES_WR fragment table; 105 refs).
- `tools/msgscan.py`: every `30`-ref lands on a string start, every string (except MESSAGE000's unused test line at 0xA78) is referenced, no entry offset points into the string area, no data after the last FF. Other opcodes seen (lengths from examples, unverified): `33` 9 B, `35` 3 B, `36` 7 B, `39` 1 B, `20` 1 B, `44` 8 B, `55` 2 B, `01` end.
- **Insertion:** re-lay the string area (strings may grow; the file can grow, DATA.SFS is rebuilt) and rewrite the u32 of each `30`/`51` ref. Bytecode and entry table do not move. The ref finder is pattern-based; the coverage check above is its proof and must run in the build (fail on any unreferenced or off-start ref).

## System text (arm9 + overlays) - verified by decode
- FONT_SYSTEM encoding, FF-terminated, strings 4-byte aligned (00 padding).
- Referenced by absolute u32 pointers: arm9 strings are at 0x02000000+off, overlay strings at 0x0211B780+off (all 20 overlays load there).
- `tools/systext.py` (-> `work/systext.tsv`) lists every aligned u32 in an image that points at a valid FF-terminated run: 1,676 candidates (arm9 1,571; ov9_03 56 = help/tutorial menu; ov9_06 19 = extras/sound test; ov9_02/15/19 = save/turn prompts; few others). It over-reports: struct fields that happen to point at data.
  - arm9 string pool: **0x8F000-0x95FFF** (unit/class/item/card names, skill and card effect descriptions, help text), plus some at 0xF5000-0xF7FFF and 0xA6000-0xA8FFF.
  - Pointer tables: 0x100000-0x101FFF (card/item/unit records, several string fields per record), 0xF5000-0xF7FFF, 0xA7000-0xA8FFF, 0xA1000; the rest are literal pools in code.
- Extract (phase 4) must decide string vs data per pointer table/record field, not per pointer: keep only fields whose targets all decode as text, and report the rest.
- **Insertion:** English longer than the slot moves to new space (arm9 can't grow in place safely; use a new overlay-free region or a DATA.SFS file loaded at boot - decide in phase 5) and every pointer to it is rewritten.
